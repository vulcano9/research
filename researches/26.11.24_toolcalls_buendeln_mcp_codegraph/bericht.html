Tool-Aufrufe bündeln, MCP-Gateways, Codegraph: Was spart wirklich Tokens?

Deep Research · 24.11.2026 · opencode v2.3.0, Claude Code, DeepSeek V4.1 Flash 1017

Kurz gesagt

  • Bündeln spart, weil jeder Schritt den ganzen Verlauf neu liest. Anthropic: „A 40-turn task sends its first turn 40 times“, die Kosten wachsen etwa mit dem Quadrat der Schrittzahl. Drei Tool-Aufrufe pro Schritt senkten in einer Studie die Kosten um 35,9 % bei gleicher oder besserer Trefferquote (W&D). opencode v2 kann das schon: parallele Tool-Aufrufe und execute (Code Mode). Claude Code führt lesende Tools parallel aus und testet seit v2.1.323 einen eigenen Code Mode.
  • Im eigenen Projekt wird kaum gebündelt. 81,5 % aller Schritte enthalten genau einen Tool-Aufruf. Fast die Hälfte der Schritte (49,9 %) sind Ketten aus reinem Lesen, Suchen und Shell. Bündeln zu Dreiergruppen hätte rechnerisch bis zu 30,9 % der Input-Tokens gespart (Obergrenze), sicher nur 5,8 % (reine Lese-Ketten). Ein bloßer Prompt-Satz „bündle“ hat im eigenen Versuch die Schrittzahl aber nicht gesenkt.
  • Ein MCP-Gateway (viele Tools hinter einem MCP) spart unter opencode v2 und Claude Code kaum noch. Beide haben die Tool-Suche schon eingebaut: opencode deckelt den Tool-Katalog auf 2.000 Tokens, Claude Code lädt MCP-Tools erst bei Bedarf. Gemessen: unter opencode 2.0.32 nur −26 % Input und etwa −12 % Kosten; unter Claude Code war ein Gateway sogar 37 bis 46 % teurer. Gateways lohnen sich für Zugangsdaten, Rechte und Protokolle, nicht fürs Sparen.
  • Ein Codegraph (ein Index der Beziehungen im Code) statt grep (Textsuche) spart nicht pauschal. Die beste Agenten-Messung: Trefferquote 89,7 % → 90,3 % (nicht signifikant), dafür +44 % Prompt-Tokens. Im eigenen Versuch mit Serena: alle Antworten richtig, aber +28 % Input und +31 % Schritte. Cursor hat seine semantische Suche wieder entfernt, Claude Code setzt auf grep. Ein Graph hilft bei „wer ruft X auf“ in sehr großen Codebasen und bei kleinen Modellen, nicht in einem HTML- und Text-Projekt wie diesem.
  • Der größte Hebel bleibt: weniger Schritte und eine kleine Grundlast. Im eigenen Versuch waren 78 bis 84 % des Inputs die Grundlast (≈ 23.600 Tokens), die in jedem Schritt neu gelesen wird. Konkrete Bausteine dafür stehen in Abschnitt 8.

„Kann man nicht Tokens sparen, indem man die Tool-Calls bündelt, wie es aktuell Claude Code macht? Bzw. MCP-Server nutzt, die die Tools hinter einem einzigen MCP bündeln? Oder auch statt grep einen Codegraphen benutzt?“

Vorbericht: Tokens sparen mit opencode, 23.11.2026

1. Warum Bündeln überhaupt etwas bringen kann

Token ist ein kleines Textstück, im Deutschen etwa drei bis vier Zeichen. Ein Schritt ist ein Request (eine Anfrage ans Modell). Der Kontext ist alles, was in diesem Request steht: System-Prompt, Tool-Beschreibungen, Instruktionsdateien, alle bisherigen Nachrichten und alle Tool-Ergebnisse. Ein Cache-Read ist ein Treffer im Zwischenspeicher des Anbieters. Er ist billiger als neuer Text, aber nicht gratis. Die Grundlast ist der Kontext des ersten Schritts: System-Prompt, Tool-Beschreibungen und Instruktionen, bevor der Agent etwas getan hat.

Ein Agent ist eine Schleife. Jeder Schritt schickt den ganzen bisherigen Verlauf noch einmal. Anthropic beschreibt das so: „by default every turn of an agentic task resends the entire growing conversation: system prompt, tool definitions, and every prior turn.“ Und: „A 40-turn task sends its first turn 40 times, so task cost grows with roughly the square of turn count.“ Quelle

Ein Schritt mit n Tool-Aufrufen ist ein einziger Request. Ein Tool-Aufruf ist ein einzelner Aufruf eines Werkzeugs; mehrere davon in einer Antwort heißen parallel. Die n Ergebnisse kommen gesammelt zurück. Bündeln senkt damit die Anzahl der Wiederholungen, nicht die Größe dessen, was wiederholt wird: Die Ergebnisse bleiben im Kontext und werden in allen Folgeschritten erneut gelesen. Quelle

Rechenbeispiel mit der Formel T·n(n+1)/2, 1.000 neue Tokens pro Schritt: 20 Schritte mit je einem Aufruf lesen 210.000 Tokens, 10 Schritte mit je zwei Aufrufen nur 110.000. Das sind 48 % weniger (Rechnung). Quelle

Eine Messung aus einem Gateway: Eine normale Feature-Umsetzung kostete 12,93 $, am Ende waren 87 % der Kosten Cache-Reads. Die Hälfte der Kosten war schon bei 27.500 Tokens Kontext erreicht (Nutzer-Messung). Quelle Im Vorbericht waren 97,1 % aller Input-Tokens Cache-Reads. Dort steht auch, warum die Grundlast und die Schrittzahl die stärksten Regler sind.

Wann Bündeln nicht spart

  • Abhängige Schritte. B braucht das Ergebnis von A, dann darf es nicht parallel laufen. Quelle
  • Große Ergebnisse bleiben im Kontext. Sie werden in allen Folgeschritten erneut gelesen, auch wenn sie gebündelt entstanden sind.
  • Code schreiben kostet selbst Tokens. Bei Mini-Aufgaben ist Code Mode teurer Quelle, bei kleinen MCP-Servern 17 bis 35 % teurer Quelle.
  • Keine Reaktion auf Zwischenergebnisse. Bei parallelen Aufrufen kann das Modell nicht nachsteuern; bei großem Schrittbudget hilft mehr Breite nicht immer. Quelle
  • Parallele Subagents sind kein Bündeln. Multi-Agent-Systeme brauchen etwa 15× mehr Tokens als ein Chat (Hersteller-Angabe). Quelle

3. Rechner: Was bringt Bündeln bei einem Subagent?

Der Rechner bildet eine Subagent-Schleife nach. G ist die Grundlast, z das Tool-Ergebnis je Aufruf, n die Schrittzahl, p der Anteil bündelbarer Schritte, b die Bündelgröße. Zusatz ist der Code, den ein gebündelter Schritt zusätzlich schreibt, o ist Output plus Reasoning je Schritt.

nb = round(n · p)  (p als Anteil, 50 % = 0,5)  ·  m = (n − nb) + ceil(nb / b)
gelesen ≈ m · G + z · n · (m − 1) / 2   (ohne Bündeln: n · G + z · n · (n − 1) / 2)
neuer Input ≈ G + n · z  ·  Cache-Read = gelesen − neuer Input
Output = m · o + ceil(nb / b) · Zusatz

Das Modell nimmt an, dass die gebündelten Aufrufe wirklich unabhängig sind, und verteilt dieselben n Tool-Ergebnisse auf m Schritte. Preise DeepSeek (eigener Fit, $ pro Mio. 6. MCP-Gateways: viele Tools hinter einem MCP

Ein Gateway (auch Aggregator oder Proxy) sitzt zwischen Agent und vielen MCP-Servern. Es kann fünf verschiedene Dinge sein, und nicht alle sparen Tokens. Notizen

7. Codegraph statt grep

grep ist eine Textsuche: Es findet Zeilen, in denen ein Muster steht. Ein Codegraph ist ein Index der Beziehungen: wer ruft wen auf, wer erbt von wem, was bricht bei einer Änderung. Embeddings oder semantische Suche finden Stellen, die „ähnlich gemeint“ sind. LSP ist der Sprachserver wie im Editor und beantwortet Definition, Referenzen und Umbenennen compiler-genau. Notizen

8. Was ich konkret tun würde

Reihenfolge nach Wirkung. Die ersten zwei Punkte bringen mehr als alle Tools zusammen.

  1. Schritte sparen bleibt der Hebel. Grundlast und Schrittzahl (siehe Vorbericht: kurze Subagents, steps-Grenze, Reasoning low für Recherche). Bündeln ist eine Ergänzung, kein Ersatz.

  2. Parallele Lese-Aufrufe ausdrücklich verlangen, aber messen. Baustein für AGENTS.md oder Agent-Dateien:

    ## Tool-Aufrufe
- Wenn du mehrere Dateien lesen oder mehrere Suchen brauchst und sie nicht voneinander abhängen,
  stelle sie als parallele Tool-Aufrufe in DERSELBEN Antwort.
- Viele gleichartige Abrufe (mehrere URLs, viele Dateien prüfen): ein `execute`-Programm mit
  `Promise.allSettled`, das nur die nötige Zusammenfassung zurückgibt.
- Shell: unabhängige Prüfbefehle in einem Aufruf ausführen, abhängige nacheinander.
- Lies erst gezielt (grep, Zeilenbereich), dann ganz.

    Ehrlich dazuschreiben: Im eigenen Versuch (B) änderte eine ähnliche Anweisung die Schrittzahl nicht. Die Wirkung eine Woche lang mit den eigenen Zahlen prüfen, zum Beispiel dem Anteil der Schritte mit genau einem Tool-Aufruf (heute 81,5 %).

  3. execute für Massenarbeit. Viele URLs, viele Dateien, Filtern großer Ergebnisse; dort ist der Effekt groß (27,4× weniger Tokens in #58708). Nicht für zwei oder drei kleine Reads. Quelle

  4. Kein MCP-Gateway zum Sparen. Code Mode nicht abschalten: Wer execute verbietet, bekommt alle MCP-Tools wieder mit voller Beschreibung in jeden Request. Quelle

  5. Codegraph nur gezielt. Für Code-Projekte mit Beziehungsfragen in einem eigenen Subagent, nicht global. Getestete Config aus dem Versuch (opencode 2.3.0, Pfad anpassen):

          "--project", "/pfad/zum/repo", "--enable-web-dashboard", "False",

}

9. Mythen-Check

Sieben Behauptungen, je mit Messung und Urteil. Zum Aufklappen.

„Bündeln spart immer“

Es spart nur bei unabhängigen Aufrufen. Die Ergebnisse bleiben im Kontext, und Mini-Aufgaben mit Code Mode werden teurer. Urteil: spart bei langen Lese-Ketten. Quelle Quelle

„Ein Satz im Prompt reicht“

Im eigenen Versuch B war die Schrittzahl genau wie in A (8,67), nur execute lief 4-mal statt 0-mal. Urteil: nicht verlässlich. Quelle

„Gateways sparen 90 %“

Herstellerzahlen beziehen sich auf Tool-Beschreibungen in Clients ohne eigene Suche. Unter opencode 2.0.32 waren es −26 % Input, unter Claude Code war ein Gateway 37 bis 46 % teurer. Urteil: hier nicht. Quelle

„Code Mode ist immer billiger“

Bei kleinen MCP-Servern kostet es 17 bis 35 % mehr Tokens Quelle. Große APIs und verkettete Aufgaben werden stark günstiger. Urteil: kommt auf die Größe an.

„Codegraph spart 40 % Tokens“

Die Zahl kommt von Herstellern (Claude Context, GPT-4o-mini). Unabhängige Agenten-Messungen zeigen +44 % (Pipeshub) und +28 % (eigener Versuch). Urteil: im Alltag nein. Quelle Quelle

„Semantische Suche ist Stand der Technik“

Cursor hat sie entfernt, Claude Code nutzt grep. Urteil: grep ist der starke Standard. Quelle Quelle

„Weniger Tool-Output-Tokens heißt weniger Kosten“

Ein Paper senkte die Tool-Ausgaben um 38,4 %, die Rechnung stieg aber um 6,8 %. Urteil: Schritte und Cache zählen, nicht die sichtbare Ausgabe. Quelle

10. Grenzen und offene Punkte

Was diese Auswertung nicht zeigen kann
  • Die R4-Ersparnis ist eine Obergrenze: Es wird angenommen, dass Aufrufe in einer Kette unabhängig sind.
  • R5: n = 2 je Zelle, ein Repo, ein Modell, Deckeneffekt, kein Signifikanztest.
  • Fast alle Gateway- und Codegraph-Zahlen stammen von Anbietern; unabhängige Replikate fehlen.
  • Es gibt keine offizielle Zahl von Anthropic zum Claude-Code-Code-Mode.
  • Es gibt keinen offiziellen Grund, warum opencode v2 das batch-Tool entfernt hat.
  • Opus-Dollarbeträge sind Gedankenpreise zum API-Preis; im Abo zählen sie aufs Limit, nicht aufs Geld.
  • opencode v2 hat (Stand 24.11.2026) kein LSP-Tool; das kann sich ändern. Quelle
